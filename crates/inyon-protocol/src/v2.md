# Protocol v2 (`/ws2`)

The hub's second app socket, for the Dioxus app. `/ws` (v1) stays as it is, so older apps keep
working. Nothing user-facing uses `/ws2` yet; this page is for contributors.

v1 sends a chat's last 160 messages again on every subscribe, the whole overview on every change and
the whole live reply on every tick. A phone that comes back from the background downloads all of
that again. v2 numbers every change so an app can say where it left off and get only what it missed.

## Streams

Each thing an app follows is a stream: `overview` (the machines and their panes), `organize` (pins,
parking, snoozes, tags, notes, projects, messages sent later, sleep rules and saved prompts, from
0.24) or a chat, named by its key `host:pane`. A stream holds rows in collections, each row with a
key, plus a few single values:

| Stream | Collections (key) | Single values (`state`) |
|---|---|---|
| `overview` | `hosts` (`config.id`) | none |
| `organize` | `sessions`, `projects`, `groups`, `spaces`, `sends`, `prompts` (`id` each), `sleep` (`scope`) | none |
| a chat | `items` (`seq`), `live` (`id`), `queue` ([`QueuedMsg::key`]) | `info`, `screen`, `draft`, `progress`, `hasMore`, `loaded` |

Every stream has an `epoch` and a `seq`. The `seq` goes up by one with each change. The `epoch` is
new whenever the hub rebuilt the stream's history: when it first has data for it, once the agent's
record has been read, when the record was rewritten (a conversation cleared or compacted into a new
file), and after the hub restarts (epochs start from the clock, so a later hub's are always larger).
Within one epoch an app is brought up to date by a delta, unless it is further behind than the
hub remembers (see below).

## Frames

Hub to app:

- `snapshot {stream, epoch, seq, rows, state}`: the stream's whole state. The app drops what it had
  for the stream and takes this. A chat snapshot with `loaded: false` has no items yet; the app keeps
  showing what it had until the next snapshot.
- `delta {stream, epoch, from, seq, remove?, replace?, append?, state?}`: the change from `from` to
  `seq`, applied in that order. `remove` takes rows out by key, `replace` swaps rows in place by key,
  `append` adds rows at the end of their collection, and `state` sets the single values it names
  (a missing one is unchanged). A live change has `from = seq - 1`. One delta can carry several
  parts, so a change that has to land at once does: the transcript row that finishes a reply comes
  in the same delta that removes the live text it replaces (records outrank live text, which outranks
  what the app guessed).
- `more {stream, items, hasMore}`: earlier messages, the answer to `more`. Not sequenced.
- `hello {v, zip?}`: the answer to the app's `hello`.

The v1 messages that aren't about streams come on the same socket unchanged: `notify`,
`page.notify`, `companion.reply`, `term.data`, `term.exit`, `pong`.

App to hub:

- `hello {v: 2, zip?: ["deflate-raw"]}`: optional, first. Without it nothing is compressed.
- `sub {stream, at?: {epoch, seq}}`: follow a stream, from where the app left it.
- `unsub {stream}`, `more {stream, before}`.
- The v1 `draft`, `term.open`, `term.in`, `term.resize`, `term.close`, `ping` and `quiet`, as they
  are. `sub.overview`, `sub.chat`, `unsub.chat` and `chat.more` are ignored on `/ws2`.

## Applying frames

The app keeps `{epoch, seq}` per stream and checks each frame against it:

| Frame | Condition | Do |
|---|---|---|
| snapshot | another epoch, or a later `seq` | apply |
| snapshot | same epoch, `seq` not later | drop |
| delta | another epoch | resync |
| delta | `seq` not later than the app's | drop (a duplicate) |
| delta | `from` is the app's `seq` | apply |
| delta | `from` later than the app's `seq` | hold it, resync |
| delta | `from` earlier, `seq` later | resync |

Resync means sending `sub` again with the app's `{epoch, seq}`. A held delta is applied once the
ones before it arrive. On one socket frames come in order, so a gap only happens around a reconnect.

## Catching up

The answer to `sub {stream, at}`:

- same epoch and `seq`: an empty delta (`from = seq`), which says the app is up to date;
- same epoch, older `seq`: one delta from the app's `seq` to the hub's, holding only the rows that
  changed since (a reply that grew 300 times in the meantime comes once, as it is now);
- another epoch, or older than what the hub still remembers: a snapshot.

For this the hub keeps, per row, the `seq` it was added and last changed at, and the keys of removed
rows (2048 per collection). It needs no log of frames. The hub keeps a stream for 30 minutes after
the last app stopped following it, so a phone that was away for a while still gets a delta; when
the chat's watcher starts again and sends its page, the stream turns that into the rows that changed.
The `organize` stream's rows come in the order the apps show them, so moving a project sends it
and the rows after it again. A session's mark is joined to a pane by `host` and `pane` while its `live`
is set (see [`SessionMark`]); the record's version (`v`) isn't sent, a `/ws2` app reads the rows as
they are.

A chat stream holds its latest 1000 messages; older ones stay with the apps that have them, and
`more` pages further back.

## Quiet

An app that sent `quiet {on: true}` (in the background) gets no stream frames, except an overview
catch-up when a machine or an agent's state changes (the same rule as v1 since 0.23.1). A change to
`organize` waits for it to come back. Its streams
stay followed, and `quiet {on: false}` brings each one up to date with one delta. There is no need to
unsubscribe chats while quiet.

## The send queue

A chat's `queue` rows are the messages on their way to the agent, owned by the hub so every device
shows the same list: prompts Inyon holds until the agent is free (`held`), messages sent through
Inyon until the agent's record has them (`send`, with their state), and what sits in the agent's own
queue (`agent`). On `/ws2` a chat's `info` carries no `sends`, `held` or `queue`.

## Compression

To an app that asked for it in `hello`, a frame of 1 KB or more ([`ZIP_MIN`]) goes out as a binary
WebSocket message holding the frame's JSON compressed with raw DEFLATE (RFC 1951). Shorter frames
go as text. Raw DEFLATE is the one format both sides already have: browsers decode it with
`new DecompressionStream('deflate-raw')`, and Rust (native and wasm32) with miniz_oxide, which is
pure Rust. Brotli compresses a little better, but browsers can't decode it from script. Each frame is
compressed on its own, so frames can be decoded in any order.
