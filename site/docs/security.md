title: Security
description: What Inyon can do on your machines, how each connection is protected, what it changes and what it reads.
---

Inyon gives whoever reaches it a shell on your machines, as the user your agents run as. A paired phone can do on a computer what you could do over SSH, and a signed-in hub can do it on every machine it reaches. Treat both like an SSH key.

## A hub

- **It stays private by default.** It listens on `127.0.0.1` until you choose a network. Reach it over a VPN or your LAN, or put it behind HTTPS. Don't expose plain HTTP to the internet.
- **One strong password.** The first visit creates it, with the setup code the hub prints. From 0.20.3 the hub prints the code itself only to a terminal; when its output goes to a log (a service, `nohup`), it prints where the code is kept instead, so someone else who can read the log can't set the password before you. The hub stores only a scrypt hash.
- **Guesses are limited.** Sign-in attempts are slowed and rate-limited per address and in total, and from 0.20.3 so is the current password that changing it asks for. Past the total limit, from 0.20.3, the hub's own machine and an address that signed in within the last 30 days carry on under their own limit, and every other address gets one try every 4 seconds between them. Wrong guesses from many addresses slow down newcomers rather than lock you out, and the hub logs it. The setup code and companion codes work the same way.
- **Sessions** are signed, HttpOnly cookies that last 30 days. Changing the password signs out every browser. The API only accepts changes from the hub's own origin. Pairing a phone or a companion app needs a password typed in the last 10 minutes; from 0.20.3 a cookie from before 0.20, which doesn't record when the password was typed, never counts as that.
- **The cookie belongs to the hub's own address.** From 0.20.3 a hub on HTTPS names its cookie `__Host-inyon_session`, which a browser accepts only from that exact address over HTTPS, so a service on a sibling subdomain, or on plain http on the same machine, can't plant one. Over plain http (a VPN address) it keeps the name `inyon_session`. The hub doesn't send `Strict-Transport-Security`: browsers ignore it on an IP address and on a certificate they were told to accept, which is how most hubs are reached. If your hub has a public name behind a proxy, set it there.
- **Behind a proxy on this machine.** The hub takes the visitor's address from `X-Forwarded-For`, and HTTPS from `X-Forwarded-Proto`, only on requests from its own machine, where a proxy would be. On a machine other people log in to, they can send those headers too and pass for another address under the per-address limit; the total limit still holds.
- **Only its own names.** The hub doesn't answer a browser that reaches it under a public domain it wasn't told about (`INYON_ALLOWED_HOSTS`), so a web page can't point its own domain at your hub (DNS rebinding) and use it from your browser.
- **Machines connect out, not in.** A machine running `inyon` opens an outbound connection to the hub; nothing on it listens. Each machine gets its own random token, the hub stores only its SHA-256, and removing the machine revokes it. A token no machine has used stops working after a day. From 0.20.3 `inyon join` trades the token in the **Add a machine** command for a new one only the machine knows, before it first connects, so the command left in your shell history, a support chat or a screen recording is dead once used. On Windows the command passes the token on PowerShell's command line, where other users of that computer could see it while it runs; it's used up the same way. A machine that joined with an older `inyon` keeps the token it had. `inyon` refuses to send its token over plain HTTP unless the hub is on the same machine or on a Tailscale or NetBird address (from 0.20; before, any private address, `localhost`, a name without a dot, or one ending in `.ts.net`, `.netbird.cloud`, `.netbird.selfhosted`, `.local`, `.lan` or `.internal`). A hub on a certificate it made itself is pinned by the SHA-256 in its **Add a machine** command: only that certificate, only from the hub's address.
- **A machine's token reads, and holds messages only if you allow it.** From 0.22 the `inyon` command on a joined machine can use that machine's token on the hub's API to list the machines, their sessions and the pages (`inyon hub machines`, `inyon sessions`, `inyon pages --hub`). It sees what a companion app sees, plus each pane's folder and program, never terminal data, chats, files, settings or how the hub reaches a machine. `inyon send` holds a message for an agent only when **Settings › Machines › Machines can message agents** is on, which it isn't until you turn it on: with it on, someone who takes over one joined machine could type into agents on all of them. Every other route answers `403`. The hub's own local token does the same on its machine, where sending needs no switch.
- **Installs fetch only what's needed.** The routes that hand Inyon to new machines (`/node`) need no sign-in, since an install script has none. From 0.20.3 they hand out the files the hub already has, and the hub fetches or builds Inyon for another system only while an **Add a machine** command is waiting to be used, or for a system one of its machines runs. Otherwise they answer `503` with "This hub hasn't fetched Inyon for … yet", so a stranger can't make the hub download about 100 MB per system.
- **Reading chats and answering questions stay on the hub's computer.** From 0.22 the hub's local token, which works only from the hub's own computer, can also read a session's latest messages (`inyon read`), answer the question on screen (`inyon answer`) and start or stop the companion agent (`inyon companion`). A joined machine's token gets `403` for all three. The [companion agent](companion-agent.md) runs on the hub's computer with these commands; it may read without asking, and a send or an answer asks you first, unless a `.claude/settings.json` you wrote in its folder allows them.
- **The `inyon` command's own token stays out of addresses.** `inyon` on the hub's machine talks to the hub with a local token. From 0.20.3 it sends the token in a header, never in a URL, where a proxy's log could keep it; the hub still takes it in the address from older `inyon` commands.
- **HTTPS on the LAN.** From 0.20 setup's *LAN* choice serves HTTPS on a certificate made for the machine, and shows its fingerprint to check in the browser. Only a VPN address gets plain http.
- **What you type stays off command lines.** From 0.20, messages, drafts, keys typed in the terminal view and API keys pasted into an agent's sign-in reach tmux on the command's input and through a file only you can read, never as a program's arguments, which other users on a shared machine could list. From 0.20.3 session names, start folders and window names reach tmux as plain text, so a folder an agent named `x#(some command)` runs nothing when you fork or restart a session in it.
- **Servers over SSH** use the hub's own `ssh` with your config and keys. The hub stores no SSH keys. It accepts a new server's host key on first contact and refuses one that changes later.
- **What it asks the internet.** Besides its own update check, from 0.17.4 the hub asks `registry.npmjs.org` for the newest version of each agent's npm package when a machine's Setup tab opens, at most once an hour per package. The request names the package and nothing else; nothing about you or your machines is sent.

## Pages

From 0.20 the hub shows the sites your agents make on its machine, such as a Blueprint plan with its mockups and progress board. An agent wrote that HTML and JavaScript, and an agent can be talked into writing anything, so the hub treats every page as untrusted.

- **Signed in to see one.** Only a signed-in browser or a paired phone can list pages or open one.
- **A link per page.** A page opens under `/v/<link>/` on the hub's own port. The link is signed with a key made from the hub's session secret, opens one page and nothing else, and lasts 12 hours. The app makes a fresh one each time you open the page.
- **No cookie under `/v/`.** Those answers never read your sign-in cookie or a phone's token, and never set a cookie. A link that is expired, revoked or altered gets "Link expired" whoever asks.
- **Ending links.** Revoking a page's links ends every link made for it so far. Removing the page does the same, from the app, with `inyon pages rm` or by editing `pages.json`, even while the hub is stopped, so a page added again under the same name doesn't open old links. Changing the hub's password ends the links of every page. A link made on a phone stops working when you forget that phone.
- **A sandbox on every answer.** Every answer under `/v/`, errors and redirects too, carries a Content-Security-Policy sandbox without `allow-same-origin`. The page runs with an origin of its own, even opened in its own tab, so it can't read the app's cookies or storage (where the app keeps the tokens of other hubs) or reach into the app's page. In its own tab the address bar still shows the hub's address, since pages share the hub's port.
- **Only its own files.** A page can load scripts, styles, images, fonts and data only from its own link's address, never from the internet or another page, and a form on it can't submit to any address. The hub also turns off DNS prefetching for it. Names starting with a dot (`.git`, `.env`, the `.inyon-page.json` marker) are never served, folders are never listed, and a file a symlink leads to outside the site's folder isn't served.
- **The app runs only its own scripts.** From 0.20.3 the hub sends the app's own page a Content-Security-Policy that allows scripts only from the app's files (`/assets/`, `theme.js`, `sw.js`). A script an agent wrote under `/v/` can't run in the app's page, even if a bug ever let a page's HTML into it.
- **The API refuses framed callers.** From 0.20 a call to the hub's API that carries the sign-in cookie is refused when it comes from a page with no origin of its own (`Origin: null`) or from another site (`Sec-Fetch-Site: cross-site`), reads included. A paired phone sends its token instead of a cookie and isn't affected. `INYON_ALLOWED_ORIGINS` names origins that may still call.
- **Folders that can't be pages.** `/`, your home folder and anything under `~/.ssh` or `~/.inyon` can't be added, judged by the path and by where its symlinks lead. A page's folder needs an `index.html`.
- **Pages on other computers** (from 0.22). The hub runs that computer's own `inyon pages get` for each file, over the connection it already has. That command reads only folders on the computer's own page list, by slug, and sends a file only when it's inside the folder with no dot name on the way; the hub then checks the answer by the rules above before serving it. Nothing on that computer listens for pages itself.
- **Nothing in a folder can stall the hub.** The hub reads a page's `progress.json` and its `.inyon-page.json` only when each is a plain file, not a symlink or a named pipe, so a pipe an agent leaves there can't hold the hub up waiting for data. `pages.json` may be a symlink, for dotfile setups, but it too is read only when it leads to a plain file, and only up to 4 MB. When you add a page, git gets 3 seconds to name its project, so a pipe in the folder's `.git` can't hold things up either: past that, the page is grouped under its own folder. `inyon pages` and Blueprint work the same way.

What the sandbox doesn't stop:

- **A page can reach the internet without being seen.** Its script can open a WebRTC connection, make the browser look up a name in DNS, move to an outside address with data in the URL, or open a window. No header or sandbox flag blocks all of these in today's browsers, and nothing on screen has to change.
- **What it can carry out** is anything the agent that wrote it could read, and anything typed into the page. An agent whose own sandbox has no network but can read your disk could copy `~/.aws/credentials` or a GitHub token into the page's folder, and the page would send it from your browser.
- **Never type the hub password into a page.** Inyon never asks you to sign in inside one. A page opened in its own tab sits at the hub's own address, so a fake sign-in form there looks real, and a password typed into it goes to the page. Today Chrome and Firefox turn their password managers off for a page with no origin of its own, as a sandboxed page is, so they shouldn't offer a saved password there. Don't rely on that. A separate hostname for pages, so a page never shares the hub's address, is planned.

## Phones paired with a hub

- Only a browser that signed in within the last 10 minutes can show a pairing code. A code works once, for 10 minutes, and five wrong tries cancel it.
- The phone gets its own random token; the hub stores only its hash. Its WebSocket connections use a single-use ticket that lasts 30 seconds, so the token never travels in a URL.
- The code carries the hub's ID, and from 0.20.2 its certificate's SHA-256 when the hub serves HTTPS itself. The app shows both before it pairs, next to the hub's address, and refuses a hub that answers with another ID.
- A paired phone can use the hub's machines but not its account: it can't change the password or pair or forget other phones.
- **Settings → Paired devices → Forget** cuts a phone off at once. Changing the hub's password doesn't unpair phones; forget them separately.

## Companion apps paired with a hub

From 0.20 an app like Legato can pair with a hub. See [Companion apps](companions.md).

- Only a browser that signed in within the last 10 minutes can make a companion code, as can `inyon hub companion-code` on the hub's computer. A code is six characters, works once, for 5 minutes, and a new code ends the last one. Eight wrong codes in a minute from one address, or thirty from all of them, stop claims for the rest of that minute.
- The app gets its own random token; the hub stores only its SHA-256.
- The hub checks the app's four permissions on every route and every WebSocket message. Everything else gets `403`, and a WebSocket frame it may not send closes the connection. It never gets terminal data, the chat history, files, uploads, settings, the account or how the hub reaches a machine (SSH targets, key files, relays), and it can't send `/` or `!` commands, control characters or escape sequences. It never sees what's typed in a box and not sent, the queue, the text of sends, or Remote Control and share links.
- What it sends reaches the agent like a message you type, so the agent may act on it within its permission mode, and **Answer** approves or declines what the agent asks. Pair only apps you trust with that.
- Its token never opens `/node`, the `/v/` pages or the `/api/local` routes of the `inyon` command.
- **Settings → Paired devices → Remove** cuts it off at once and closes its connection. Changing the hub's password doesn't remove companion apps; remove them separately.

## Computers paired with the phone

A paired phone gets a shell on the computer as the user running `inyon`, the same as SSH.

- **The pairing code is the secret.** It works for 10 minutes and for one phone. Don't share a screenshot of it. `inyon forget` revokes a phone.
- **No link in a pane Inyon shows.** Inyon shows every tmux pane in the app, and a companion app can read an agent's screen. So from 0.20.3 `inyon pair` run inside tmux leaves out the `inyon://pair` link, which pairs a phone by itself, and says why; `inyon pair --show-link` prints it. The QR code and the typed code still show there, so pair from a terminal outside tmux when others can see the pane.
- **Typed codes.** The ID and the 6-digit code together pick out the computer's record on the relays, through a slow key derivation, so knowing the ID alone doesn't let anyone stand in for the computer. Whoever has both could publish a record under them too, so from 0.20.3 the computer checks that record every 20 seconds while its code is open and stops the typed code if another computer has taken it over, and the app shows the computer's ID after it pairs from a typed code. If it isn't the ID `inyon pair` printed, remove that computer. From 0.17.4, typing a code needs both the app and the computer on that version or newer; the QR code and the link work across versions.
- **End-to-end encrypted.** Phone and computer run Noise IK (X25519, ChaCha20-Poly1305, SHA-256). The phone already knows the computer's key from the code, so a tunnel, relay or network in between can't read or change the traffic, or pretend to be the computer. The computer only lets in phone keys it has paired.
- **The tunnel is public; the listener isn't open.** The Cloudflare quick tunnel gives the computer a public address, but it only reaches the link on `127.0.0.1`. Without the handshake, the link answers plain HTTP with a fixed `inyon` and nothing else, so anyone can tell an Inyon computer answers there, and nothing more. From 0.20.3 a phone it doesn't know isn't told the computer's name either. The link also listens on private-network addresses (not on Windows) with the same handshake; `--no-vpn` turns that off.
- **Strangers can't pile up work.** From 0.22 the link holds at most 64 connections that haven't finished the handshake, through the tunnel and the relays together, and closes the next one at once. Every connection through the tunnel comes from `127.0.0.1`, so the cap counts them all rather than per address. A relay gets at most 64 sessions. A phone or relay that stops reading is cut off once 8 MB is waiting for it, so terminal output can't fill the computer's memory, and refused connections write one line to the log and then at most one a minute that counts the rest.
- **A relay answer works at that relay only.** A computer that uses a relay (`--relay`) proves its ID there by signing the relay's challenge. From 0.22 it doesn't answer a challenge shorter than 16 characters, and when the relay asks for version 2 the signature names the relay's own address as the computer dialed it, so one relay can't pass another relay's challenge on and sign in there as the computer.
- **`--lan` listens on every interface.** With the local network on, the link listens on all of the computer's addresses. From 0.20.3 it publishes only private, link-local and VPN (`100.64.0.0/10`) ones, so a server's public address doesn't end up in its signed record.
- **One key for everything.** The phone uses one ed25519 key for SSH servers and for every computer it pairs with, so they all see the same public key and could tell it's the same phone, and anyone who got that key could use it on all of them. Keep it on the phone; Forget and Remove revoke it one place at a time.
- **Addresses are signed.** The computer publishes where it can be reached as a pkarr record signed by its own key. The record names addresses only.
- **Keys** live in `~/.inyon/node/`, readable only by you.
- **Logs are yours alone.** From 0.20.3 the logs a background start writes (launchd on macOS, a `nohup` start, `inyon update --background`) are readable only by you, in a folder only you can open.

## The Android app

The app is its own hub, so whoever holds the unlocked phone can reach your computers and servers, as with a terminal app that has your keys.

- **Host keys are pinned.** The app shows a server's fingerprint before the first sign-in and stores the one you trust. A different key later stops the connection until you confirm it.
- **Secrets stay on the phone.** The app's ed25519 key, passwords, pasted keys and, from 0.20.2, each paired hub's token live in Android's encrypted storage, under a key in the phone's Keystore. Backups and device transfer are off: neither a cloud backup nor moving to a new phone (Android 12 and later) copies any of the app's data, so a new phone pairs again.
- **Plain http only where it's private.** From 0.20.2 the app sends nothing to a plain `http://` hub unless it's this phone, a Tailscale or NetBird address, or a name that points only there, the same rule as `inyon join`. A NetBird name may also have an IPv6 address, which NetBird picks at random in a unique-local range (`fd…`), so one is accepted beside the name's `100.x` address and refused alone. Android can't allow cleartext by address range, so the app checks each hub itself before it sends anything. A name is looked up on every new connection; a name that answers differently to the app than to the WebView a moment later isn't caught.
- **A pairing code shows where it leads.** From 0.20.2 the app shows a hub's address and ID, and a computer's ID, before it pairs, and pairs only on a tap. The hub's web app and `inyon pair` show the same ID under their code.
- **Only Inyon's own notifications open a screen.** The app opens a path from a notification only when the tap carries a random value this install made, so another app on the phone can't send it to a pairing screen.
- **Agent pages can't reach the app.** A page under `/v/` shown in the app's sandboxed frame sees no native object: Capacitor's bridge answers only the app's own top frame, and from 0.20.2 the app removes the two JavaScript interfaces Capacitor adds to every frame. On a WebView too old for that (before WebMessageListener), the app opens pages and previews in the browser instead of a frame. The release build checks this on an emulator.
- **Nothing in between.** SSH goes straight from the phone to the server.

## Notifications

- **A hub** sends Web Push to the browsers registered with it, at most 20, from 0.20.3: a 21st registration drops the one made longest ago. A companion app can't add or remove one.
- **A computer** sending to a [browser copy](browser-copy.md) keeps that browser's push subscription in `~/.inyon/node/push.json`, readable only by you. Each message is encrypted to that browser (RFC 8291), so the push service (Google, Mozilla or Apple) sees only ciphertext. `inyon forget` drops that phone's subscriptions. The browser shares its push key with each computer that sends to it; from 0.20.3, removing a computer in the app makes the browser a new key and subscribes again, so a removed computer can't send it anything.
- **A tap opens Inyon, and only Inyon.** From 0.20.2 a notification opens a screen of the Inyon it came from; a link to another site or another path in the message is ignored and the tap opens Inyon's home.

## What Inyon changes on a machine

One small file on its own: `~/.inyon/machine-kind`, where the hub's check notes whether the machine is a laptop, a desktop or a server, and looks again once a day. Nothing else, unless you turn on the Claude Code integration from the machine's Integration tab (or switch a Claude Code model, below). Then it:

- writes `~/.inyon/hook.sh` and `~/.inyon/statusline.sh`, and registers them in `~/.claude/settings.json`, backing that file up first to `settings.json.inyon-backup`. From 0.22.2 a `settings.json` that links to your dotfiles stays a link (the file it points to is changed), and Inyon writes only if the file is still as it read it, so a setting Claude Code saved in between isn't lost. The hook runs on session start and end, a prompt, a notification, a permission request and the end of a turn, plus, from 0.22 with Claude Code 2.1.78 or later, a turn that ended on an error (StopFailure). Older Claude Code doesn't get that one, since before 2.1.101 an event it didn't know made it ignore the whole settings file. From 0.22.1 the hook and the hub's check also read Claude Code's own session records in `~/.claude/sessions`, without changing them, to find the window a background session belongs to;
- keeps your own status line in `~/.inyon/statusline.orig` and still runs it;
- does the same for Antigravity CLI in `~/.gemini/antigravity-cli/settings.json`, if it's installed;
- from 0.22, adds the same hook to the other agents that run hooks, when they're installed: GitHub Copilot CLI gets a file of its own, `~/.copilot/hooks/inyon.json`; Gemini CLI an entry on each of its events in `~/.gemini/settings.json` (backed up first to `settings.json.inyon-backup`); Antigravity CLI an entry named `inyon` in `~/.gemini/config/hooks.json` (backed up the same way). Each runs on a prompt, the end of a turn and a session starting or ending, Copilot's and Gemini's on a notification too, and Copilot's on an error. The hook only logs the event for its pane and answers with an empty `{}`, so it never decides anything for the agent, and an entry left behind with no `~/.inyon/hook.sh` does nothing. Copilot's permission requests are left alone, because an answer there would grant or refuse the permission. Codex isn't included: its hooks run in a background process that can't tell which pane they're for, and only after you trust them;
- puts the integration back, at most once every ten minutes, if something else rewrites `settings.json`;
- for a session that was already running when its settings were replaced, adds the status line to that project's `.claude/settings.local.json` (only if it has none) and lists that file in `.git/info/exclude`, so git never sees it.

Turning the integration off undoes all of it. The hub's fallback in Bun (`INYON_HUB_IMPL=bun`) adds and removes only Claude Code's and Antigravity CLI's status line parts, so turn the integration off from the Rust hub to take the other agents' hooks out. The hook's log holds your prompts, so `~/.inyon` is readable only by you.

From 0.22 the hub also resizes the tmux window of an agent that no tmux client shows to 200×50, so its screen reads whole (see [The terminal](terminal.md#window-size)). A window a client shows, or one with a `window-size` of its own, is left alone.

From 0.22, starting the [companion agent](companion-agent.md#what-asks-first) with Codex writes `~/.inyon/companion/.codex/rules/companion.rules` and adds that folder to `~/.codex/config.toml` as trusted, so Codex reads the rule that makes a send or an answer ask first. It adds the entry only when the file doesn't name the folder yet, and stopping the companion leaves both in place.

On Windows, setup also adds Inyon to the Start menu (a shortcut in your own Start menu folder) and to Settings → Apps (a key under `HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Uninstall\Inyon`), and registers the scheduled task that opens the Inyon app at sign-in, all for your user only, with no administrator rights. From 0.20.3 nothing runs in the background except as the Inyon app's children, in a Windows job that ends them when the app ends, and the app shows its icon while anything runs. The `inyon` command leaves requests for the app in `~/.inyon/node/app-requests`, readable only by you, and the app answers there. `inyon uninstall` removes all of it.

On Windows, ticking *LAN* or *VPN* in setup adds one firewall rule, "Inyon link", once an administrator allows it. From 0.20.3 the administrator PowerShell gets its few lines in its own command, not from a file another program could change before it runs. It lets in TCP on the link's port, to `inyon-engine.exe` only, from the local network and the VPN address ranges. From 0.19 that file is the copy of `inyon.exe` without a console, and the link runs from it even when you start it in a terminal, or when `inyon pair` starts it because none was running. `inyon uninstall` removes it.

Switching a Claude Code session's model or effort from Inyon touches `settings.json` too, with or without the integration: Claude Code saves the pick there as your default, and from 0.17.1 Inyon puts the old `model`, `effortLevel` and `modelSettings` values back (see [Controls](controls.md#model-effort-and-mode)). It only replaces the file if it hasn't changed since Inyon read it, and leaves every other byte as it was.

Uploads go to `~/.inyon/uploads` and are deleted after the period you choose. From 0.17 a computer also deletes them by itself when no hub does, and an upload that broke off halfway is deleted after an hour. Files with secrets (the integration's settings, a pasted prompt, a token file) are written readable only by you from the first byte, and a temporary file is removed even when the write is interrupted.

## Removing a machine cleans it up

From 0.17, removing a machine that can be reached takes back what Inyon put there before it goes: the Claude Code and Antigravity integration (your own status line comes back), the uploads, the prompt log and the SSH connection the hub kept open to it. Removing a server the phone reached with its phone key also takes that key out of the server's `~/.ssh/authorized_keys`, and nothing else in the file changes. Removing a paired computer from the phone unpairs the phone on that computer too. If the computer is off, from 0.20.3 the app says the computer still trusts the phone and tells it to forget the phone once it's back online, for up to a month; `inyon forget` on that computer ends it at once. A machine that's off or out of reach is removed anyway; run `inyon uninstall --purge` on it later, or delete the files by hand.

## What Inyon reads

For Claude's plan limits, the hub runs a short script on the machine that reads Claude Code's access token from `~/.claude/.credentials.json` (or the macOS Keychain) and asks `api.anthropic.com` for the account's usage, as `/usage` does. The token goes to `curl` on stdin, so it never appears in the process list, and it never leaves that machine. Only the percentages and reset times come back.

For Codex's plan limits (from 0.21), the hub runs `codex app-server` on the machine for a moment and asks it for the account's limits, as Codex's own window does. Codex uses its own login; nothing is read from its files, and the account id in the answer is removed before it leaves the machine. This happens every five minutes while someone has Inyon open, and not at all while nobody does.

From 0.17 the **Files** tab and **Changes → Working tree** read the session's folder on the machine while you have them open: a folder listing, one file, or `git status` and one file's diff. Nothing is kept on the hub or the phone. **Commit all** and **Push** run only when you press them, as your user, with git's own hooks and signing.

From 0.17.6, OpenCode's providers are OpenCode's own business. Connecting one runs `opencode auth login -p <provider>` on that machine, in a tmux session of its own: a key you type in the app is typed into that command and goes nowhere else, is never logged, and Inyon never reads `auth.json`, where OpenCode keeps it. Listing providers runs `opencode auth list`, which prints names and kinds, never values; when no OpenCode session of Inyon's is running on the machine, it also starts `opencode serve` on `127.0.0.1` for a few seconds in an empty folder to read the provider catalogue, and stops it. Disconnecting runs `opencode auth logout`.

## Downloads

Every release ships a `SHA256SUMS` file, and from 0.14 a minisign signature of it, `SHA256SUMS.minisig`, made with Inyon's release key:

```
RWRTvQv/ifQnD3jarY1oarS0AKdhogH+mdgn/o0NzT/Ro8L43nFqqfp6
```

- `inyon update` and `inyon setup` refuse a list without a good signature before they download anything. The key is built into `inyon`, so an environment variable can't swap it for the real releases, on this site or on GitHub.
- Installs and updates download from this site. Its `latest.json`, which names the newest version, isn't signed, so it only chooses what to fetch: `inyon update` also checks that the signed list names that version's APK, and refuses an old or altered copy. This ties each release to its Android build: if that build fails, machines stay on the version they have until the release is complete, rather than take one that isn't.
- From 0.20 the installers this site serves at `/get.sh` and `/get.ps1` carry the sha256 of the list the site checked when it published the release, and trust no other list. That one line is all that differs from the copies in `/download/` and on the release. Anywhere else they check the signature with `minisign` and that the list names the APK of the version they asked for, so an older release's list is refused. Without `minisign` they stop, unless told to go on with `--no-signature-check`. Either way they check every download against the list before running it.
- A hub hands its own version's files to its machines, so a machine always runs what its hub runs. The **Add a machine** command carries the checksum of the hub's list, which covers the first install; updates are checked as the next point says. From 0.20 the hub itself checks the release's signature with the same built-in key before it hands out or lists any file, including from a mirror set with `INYON_DOWNLOAD`, and answers 502 when the signature is missing or wrong.
- From 0.20 a machine that updates from its hub, or fetches its engine there, checks what it downloads against the release's signed `SHA256SUMS`, which the hub passes on with its signature, never against a checksum only the hub gives. The list has to name the APK of the version the hub says it runs, as `inyon update` asks of this site, so an older release's list can't be passed off as the hub's; the hub holds the release it fetches to the same rule. A hub from before 0.20, or one running from a checkout, has no signed list, and the machine changes nothing until the hub is updated or `INYON_ALLOW_INSECURE=1` says to take the hub's checksums.
- From 0.19 a computer that isn't a hub downloads one program, `inyon`, and no longer the Bun engine. On Windows, `inyon-engine.exe` is made on the computer from the checked `inyon.exe`, with one header field changed so it opens no console.
- The files on this site are copied from the release. The site's build checks the signature and every file's checksum, and publishes nothing if one fails. From 0.20 the installers are in the signed list too; for an older release the site takes them only when they're byte for byte the ones in the commit the release is tagged on. A new release appears here only once its APK is listed in the signed list.
- In the release workflows, only the jobs that publish can change a release. They install nothing but Ubuntu's `minisign` package, to sign, and never install or run the project's dependencies. The Android build lists its APK in `SHA256SUMS` and signs it again only after the list's own signature checks out against the release key, and only once the APK on the release is the one it built.
- The npm packages (`@abhash-chakraborty/inyon` and one per system) are published only by the release workflow on GitHub, through npm's trusted publishing, so no npm token is stored for them. The workflow copies the programs from the release after checking the signature and every checksum, and each version carries a provenance statement naming the run that published it. `npm audit signatures` checks that after installing.
- `cloudflared` is pinned to one version and checked against a known hash.

[Checking a download](/download/#verify) shows how to check a file by hand.

## Reporting a vulnerability

Please report it privately through [GitHub's vulnerability reporting](https://github.com/Abhash-Chakraborty/inyon/security/advisories/new) rather than in a public issue, with steps to reproduce. You'll get a reply within a few days.

The same address is in [`/.well-known/security.txt`](https://inyon.tech/.well-known/security.txt) (RFC 9116), for scanners and researchers that look there. What this site, `inyon` and the Android app send to other services is listed in the [privacy policy](/privacy/).

## This website

The site is static files on GitHub Pages. It sets no cookies and has no analytics. Its fonts, styles and scripts are served from the site itself, and every page carries a Content-Security-Policy that lets it load nothing else, apart from the Product Hunt badge on the home page and the video, which loads from YouTube's privacy-enhanced domain only when you press play.
